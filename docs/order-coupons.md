# 쿠폰 PR 2 — 주문 예약 및 결제 실패 복구

관련 이슈: #470, 상위 계획: #473. PR 1(#469, PR #474)이 선행한다.

## 결제 요청

기존 `POST /payments`에 선택적 정수 `couponMultiplier`를 추가한다.
`2` 또는 `3`만 허용하며 생략·`null`은 미사용이다. 응답 성공 구조는 기존과 같다.
인증된 결제자의 쿠폰만 선택하며 공개 예약·복구 API는 만들지 않는다.

| 상황 | HTTP | 오류 코드 |
| --- | --- | --- |
| 2·3 이외 배수 | 400 | INVALID_REQUEST |
| 본인의 사용 가능 수량 부족 | 422 | COUPON_NOT_AVAILABLE |
| 같은 결제자·멱등키로 쿠폰 선택 변경 | 409 | IDEMPOTENCY_KEY_CONFLICT |
| PR3 전 쿠폰 결제 차단 | 409 | CONFLICT |

오류는 기존 `{message, error: {code, traceId, details?}}` 구조다.
입력 범위 오류는 `details`에 `couponMultiplier` / `OUT_OF_RANGE`를 포함한다.
쿠폰 미사용 요청의 해시는 기존과 같으며 쿠폰 선택 시에만 배수를 해시에 추가한다.

## 테이블 및 상태

V39에서 `order_coupon_usages`를 추가한다. 주문에는 보상액·배수 스냅샷을 추가하지 않는다.

| 필드 | 타입 | NULL | 역할 |
| --- | --- | --- | --- |
| id | BIGINT | 불가 | 자동 증가 PK |
| order_record_id | BIGINT | 불가 | orders.id FK, UNIQUE로 주문당 한 기록 |
| coupon_inventory_id | BIGINT | 불가 | coupon_inventories.id FK |
| status | VARCHAR(20) | 불가 | RESERVED / USED / RESTORED CHECK |
| created_at | DATETIME(6) | 불가 | 생성 시각 |
| updated_at | DATETIME(6) | 불가 | 변경 시각 |

배수는 연결된 수량 행에서 확인한다. 상태 USED는 PR3 사용 확정을 위해 정의하며 PR2에서는 전이하지 않는다.
두 FK 모두 별도 PK를 참조하는 비식별 관계이며 삭제 cascade는 없다.

- 주문 생성과 수량 1개 차감·RESERVED 저장은 같은 트랜잭션이다.
- `quantity > 0` 조건부 UPDATE로 잔여 수량을 초과하는 예약을 막는다.
- 같은 주문의 예약·복구는 주문 행을 잠금 조회하고 반복 요청을 중복 반영하지 않는다.
- 결제 거절 확정 또는 로컬 처리 실패에 따른 자동 취소 확정 시 RESTORED로 바꾸고 1개 복구한다.
- 결과 미확정 및 운영 확인 대상은 예약을 유지한다. 복구 실패 시 주문 변경도 롤백한다.
- 이미 승인된 결과를 늦게 도착한 거절로 덮어쓰지 않는다.

## 개방 및 검증

PR2 시점의 `app.coupon.payment-enabled` 기본값은 false였다. 아래 PR3 구현에서는 사용 확정·배수 보상 지급을 연결했고 현재 코드의 기본값은 true다. 배포 환경의 실제 설정을 확인한다.

자동 테스트는 MySQL에서 동시 예약, 멱등성, 소유권, 실패 복구, 미확정 유지, 롤백을 검증한다.
전체 테스트의 컨텍스트 캐시는 최대 8개로 제한하며 힙 증설은 하지 않는다.

Postman `payment-api.postman_collection.json`의 `05. PR2 쿠폰 요청 검증`은
기존 00·01 폴더 실행 후 기본 차단 설정에서 배수 입력·차단·선택 변경 충돌을 확인한다.
컬렉션 JSON과 스크립트 문법만 확인했으며 실제 서버를 통한 PR2 수동 검증은 미실행이다.
실제 결제 서버의 쿠폰 성공 경로와 룰렛 연동은 후속 검증으로 남긴다.

## PR3 후속 구현 및 검증

결제·발송 확정 시 RESERVED → USED로 확정하고, 보상은 기존처럼 상대방 수락 완료 시 지급한다.
기본 50,000 × 주문의 사용 확정 쿠폰 배수(미사용 1 / 쿠폰 2·3)를 적용한다.
기존 미수락 선물에도 새 기본 보상을 적용하고, 이미 지급한 과거 원장은 보존한다.
미수락 취소·만료가 확정되면 환불·취소 처리와 USED → RESTORED·수량 1개 복구를 같은 트랜잭션으로 처리한다.
취소 진행·결과 미확정 동안에는 수락을 차단하며 단순 수락 대기에는 쿠폰을 복구하지 않는다.

기존 GIFT_COMPLETED_REWARD 알림에 실제 지급액과 적용 배수를 표시한다.
수락 상태·잔액·보상 원장이 커밋된 뒤 알림을 생성하고, 재수락에는 다시 발행하지 않는다.
보상 알림은 기존 AFTER_COMMIT 경로를 사용하므로 보상 트랜잭션 자체와 하나의 원자적 커밋은 아니다.
알림 저장 장애의 재시작 복구는 이번 변경의 검증 범위에 포함하지 않는다.

[PR3 Postman 준비·실행 및 검증 범위](postman/coupon-payment-api.md)를 따른다.
기존 PR2 기본 차단 컬렉션과 PR3 활성화 컬렉션의 실행 환경을 구분한다.

## 결제 서버 입력 거절(400)과 트랜잭션 경계

주문 생성·쿠폰 RESERVED 저장·수량 차감은 같은 트랜잭션이지만 외부 승인 요청 전에 커밋된다.
외부 결제 HTTP 요청은 이 DB 트랜잭션에 포함되지 않으므로 이후 400이 발생해도 예약이 자동 롤백되지는 않는다.

- DTO·인증·멱등키 검증 단계의 입력 오류는 주문 예약 전에 거부한다.
- 앞선 미확정 시도 없이 외부 승인 요청이 즉시 INVALID_REQUEST로 거절되면 기존 결제 거절 확정 경로로 연결한다. 주문 DECLINED와 예약 RESTORED·수량 복구는 같은 트랜잭션이다. 최초 응답은 400 INVALID_REQUEST이며 종료된 같은 주문 재요청에는 기존 PAYMENT_DECLINED 결과를 사용한다.
- 승인 요청 전에 기존 approval_result를 NULL → UNKNOWN으로 조건부 갱신해 한 요청만 승인 명령을 전송한다. 동시 요청이나 이미 미확정인 요청은 승인 명령을 다시 보내지 않고 같은 주문의 결과를 조회한다. 입력 거절로 쿠폰을 반환한 뒤 다른 동시 요청이 같은 주문을 승인시키는 것을 막는다.
- PaymentClient 내부의 기존 동일 주문 승인 재시도는 유지한다. 외부 호출 중에는 주문 행 잠금을 유지하지 않는다.
- PaymentCommandRetry에서 앞선 타임아웃·일시 장애·PENDING 응답 이후 재시도 중 오류가 발생하면 예외에 outcomeUncertain을 보존한다. 마지막 응답이 400·401·거절이어도 승인·취소 서비스는 해당 오류만으로 실패를 확정하지 않고 결과를 조회한다. 원본 오류·추적값·원인은 보존한다.
- 재시도 후 승인 결과가 COMPLETED이면 쿠폰을 USED로 확정하고, DECLINED이면 예약을 복구한다. 조회 실패·기록 없음·PENDING이면 예약을 유지한다. 취소 재시도도 실제 취소 완료를 확인한 경우에만 보상 처리로 연결하며, 확인되지 않은 취소를 DECLINED로 종료해 수락을 허용하지 않는다.
- 타임아웃·응답 유실·결과 조회 실패·조회 시 PAYMENT_NOT_FOUND만으로는 결제 실패를 확정하지 않는다. 주문을 미확정 상태로 유지하고 쿠폰도 예약한 채 기존 재조정/운영 확인 경로를 사용한다.
- 승인 전송 권한을 확보한 직후 프로세스가 종료된 경우에도 결과가 미확정이므로 조회 및 운영 확인으로 처리한다. 중복 승인을 피하기 위해 새로운 승인 명령을 자동으로 전송하지 않는다.

수정 전 400으로 남아 있는 예약을 일괄 증가시키지는 않는다. 기존 주문은 실제 결제 서버의 승인·미승인 상태와 진행 중 요청을 확인한 뒤 주문별로 정리해야 한다. 쿠폰 수량만 임의 증가시키면 나중에 승인되거나 중복 복구될 수 있다.

## 최초 인증 실패 및 사용자 취소 보완

| 상황 | 기존 흐름 | 보완 후 흐름 |
| --- | --- | --- |
| 최초 승인 401 | 오류만 반환하고 주문 PENDING·쿠폰 RESERVED 유지 | 주문 DECLINED와 쿠폰 RESTORED·수량 1개 복구를 같은 트랜잭션으로 처리 |
| 최초 사용자 취소 400 INVALID_REQUEST·401 | 취소 PENDING이 남아 선물 수락 차단 | 취소 기록만 DECLINED로 종료. 결제 COMPLETED·쿠폰 USED 유지, 다른 진행 중 취소가 없으면 수락 허용 |
| 앞선 미확정 시도 이후 400·401 | 마지막 오류만으로 실패 처리할 위험 | outcomeUncertain을 확인해 최종 결과 조회. 결과 미확정이면 주문·쿠폰 예약 또는 취소 차단 유지 |
| 동일 사용자 취소의 동시 요청 | 같은 취소 명령을 각 실행에서 전송 가능 | 한 실행만 전송 선점. 나머지는 동일 요청 키의 취소 결과만 조회 |
| 만료·자동 보상 취소의 인증 실패 | 같은 시스템 요청 키로 후속 재시도 | 기존 재시도 유지. 사용자 취소 선점·인증 거절 종료를 적용하지 않음 |

승인 claim()은 기존 NULL → UNKNOWN 조건부 갱신을 유지한다. UNKNOWN은 BE가 승인 결과를 확정하지 못했음을 뜻하며 그 값만으로 쿠폰을 복구하지 않는다. 별도 요청 시각 컬럼은 추가하지 않는다.

사용자 취소는 PENDING·failure_code NULL인 행의 failure_code를 CANCELLATION_RESULT_UNCONFIRMED로 조건부 갱신한 실행만 외부 명령을 시작한다. 이 값은 외부 결과를 아직 확정하지 못했음을 표시한다. 즉시 거절이면 해당 취소만 종료하고, 성공이면 기존 환불·쿠폰 복구 트랜잭션으로 연결한다. 종료한 취소의 동일 키는 기존 거절 결과를 반환한다. 다시 취소하려면 새로운 요청 키를 사용한다.

재시도 이력이 있는 401이나 조회 API의 401은 즉시 거절로 확정하지 않는다. 승인 성공 가능성이 있는 주문의 예약을 복구하거나 실제 취소 가능성이 있는 선물의 수락을 허용하지 않는다.

### 배포 및 기존 데이터

V40은 기존 USER·PENDING·failure_code NULL 행만 결과 미확정으로 표시한다. 이미 전송됐을 수 있는 취소를 신규 전송 대상으로 재사용하지 않으며, 쿠폰 수량·자동 취소 기록·완료 기록은 변경하지 않는다.

기존 main 서버로 유입되는 요청을 중단하고 진행 중 요청을 종료한 뒤 V40을 적용하고 새 버전을 기동한다. 구버전 서버가 계속 취소 명령을 전송하는 혼합 배포는 피한다. 기존 미확정 건은 실제 결제 결과를 확인한 뒤 정리하며 수량만 임의 복구하지 않는다.

선점 직후 외부 전송 전에 프로세스가 종료되면 결과 조회 및 운영 확인이 필요하다. 최초 승인 401은 외부 서버 간 인증 문제이므로 사용자 로그인 401로 변환하지 않고 기존 결제 처리 오류 응답을 유지한다. API·테이블 컬럼 추가는 없다.

### 검증 범위

자동 테스트는 최초 승인 401의 1회 복구, 사용자 취소 400·401 이후 결제·쿠폰 유지 및 수락, 새 키 취소 재시도, 동일 취소의 동시 실행, 재시도 후 401의 결과 조회, 만료·자동 취소 재시도, V40의 기존 기록 보존을 검증한다. 서비스 테스트의 외부 결제 응답은 Mock이며 실제 서버 장애 주입 검증은 별도다.

2026-10-26 최종 자동 검증: 메인 서버 전체 테스트 총 1,742개 중 1,733개 통과·9개 건너뜀·실패 0개. Postman 스크립트 모의 실행은 62개 요청·235개 검증 통과, 6개 잘못된 결과 사례 검출, 95개 스크립트 문법 확인 완료. `git diff --check` 통과. 실제 Postman 실행은 환경 파일의 로그인 비밀번호·토큰이 비어 있어 미실행이며 수동 확인 항목으로 남긴다.
