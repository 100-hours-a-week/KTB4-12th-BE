# PR3 쿠폰 결제·수락 보상·알림 검증

## 준비

1. `coupon-payment-api.postman_collection.json`과 `coupon-payment-local.postman_environment.json`을 가져온다.
2. 로컬 main-backend와 payment-server를 실행한다. 검증할 main-backend에 `app.coupon.payment-enabled=true`를 적용한다. 환경변수 이름은 `APP_COUPON_PAYMENT_ENABLED`다. 저장소의 기본 false 설정은 변경하지 않았다.
3. 환경에 발신자·수신자의 테스트 계정 이메일/비밀번호와 구매 가능한 `productId`, `quantity`를 설정한다. 두 계정은 서로 다른 사용자이고 친구 관계여야 한다. 실제 비밀번호·토큰을 저장소에 커밋하지 않는다.
4. 발신자에게 충분한 결제 크레딧과 **2배 쿠폰 2개 이상, 3배 쿠폰 1개 이상**을 준비한다. 쿠폰 초기 행은 회원가입 때 생성된다. 공개 쿠폰 발급 API는 없으며 이 컬렉션은 보유 쿠폰을 사용한다. 반복 실행할 때도 필요한 수량을 다시 준비한다.
5. 수락용 선물 3건과 취소용 선물 1건을 생성하므로 테스트 전용 계정·상품을 사용하고, 실행 중 같은 계정으로 다른 결제·크레딧 사용을 하지 않는다. 잔액 비교는 다른 크레딧 변경이 없다는 전제다.

`quantity=1` 기준 전체 실행의 결제 요청은 4건이다. 취소용 1건은 환불되지만 수락한 3건은 유지된다. 상품 수량이 여러 개여도 주문 한 건당 보상 1회·쿠폰 1개를 적용한다.

## 실행

`Coupon Payment PR3 Local` 환경을 선택하고 Collection Runner에서 폴더 순서대로 실행한다. 각 폴더의 내부 요청도 순서를 유지한다. 상태를 저장하는 변수는 `pr3_` 접두사를 쓰며 최초 결제/취소 시 새 멱등키를 만들고 재요청에서는 같은 키를 재사용한다.

| 폴더 | 검증 |
| --- | --- |
| 00 인증 | 발신자·수신자 로그인 및 토큰 저장 |
| 01 쿠폰 미사용 | 결제 직후 미지급, 수락 시 50,000, 재수락 중복 지급 없음, 기본 보상 알림 |
| 02 2배 쿠폰 | 수량 1개 차감, 수락 시 100,000, 2배 쿠폰 적용 알림 |
| 03 3배 쿠폰 | 수락 시 150,000, 3배 쿠폰 적용 알림 |
| 04 미수락 취소 | 2배 쿠폰 사용 후 취소, 결제 금액 환불·쿠폰 1회 복구, 보상 알림 없음 |

정상 승인은 `X-Payment-Scenario` 헤더 없이 요청한다. 결제 서버는 헤더가 없으면 기본 APPROVE로 처리한다. 해당 헤더를 명시하면 local/test/dev 프로필에서만 허용되며 default 프로필에서는 400으로 거절되므로 PR3 컬렉션에서는 보내지 않는다. 예상과 달리 202 또는 오류가 반환되면 해당 검증은 실패한다. 컬렉션이 결과 미확정을 성공으로 처리하거나 새 키로 자동 재결제하지는 않는다.

보상 알림은 `/notifications`의 `data.items`에서 현재 선물의 `referenceId`와 `GIFT_COMPLETED_REWARD` 타입으로 찾는다. `data.pagination`에 다음 페이지가 있으면 추가 조회한다. 최대 20페이지까지 탐색하고 초과·잘못된 커서는 실패 처리한다. 테스트 계정의 알림이 너무 많으면 별도 계정을 준비한다.

## 알림 기대값

| 선택 | 제목 | 메시지의 핵심 내용 |
| --- | --- | --- |
| 미사용 | 보상이 지급되었어요 | 선물 완료 보상 50,000 크레딧 |
| 2배 | 2배 쿠폰 보상이 지급되었어요 | 2배 쿠폰 적용, 총 100,000 크레딧 |
| 3배 | 3배 쿠폰 보상이 지급되었어요 | 3배 쿠폰 적용, 총 150,000 크레딧 |

상품명은 서버의 기존 축약 정책을 따르므로 Postman에서는 제목과 금액·배수 문구를 검증한다. Java 통합 테스트는 실제 저장된 전체 제목·메시지·선물 참조·중복 방지 키까지 확인한다.

## 기존 컬렉션과의 관계

- `payment-api.postman_collection.json`의 기존 쿠폰 미사용 수락 기대값도 50,000으로 변경했다.
- 기존 `05. PR2 쿠폰 요청 검증` 폴더는 **쿠폰 결제 기본 차단(false)** 상태를 검증한다. PR3 활성화 환경에서 해당 폴더의 차단 검증을 함께 실행하면 실패하는 것이 정상이다. PR3 전용 컬렉션과 실행 환경을 구분한다.
- PR3의 결제 응답 `balanceAfter`는 결제 차감 후 잔액이다. 상대방 수락 전에는 보상을 포함하지 않는다.
- 기존 미수락 선물에도 새 기본 보상 50,000을 적용한다. 이미 지급한 과거 선물의 원장은 변경하지 않고 재수락 시 기존 지급액을 반환한다.

## 자동 테스트와 수동 검증 구분

Java 자동 테스트는 MySQL에서 결제·수락·쿠폰 확정, 동시 요청, 미수락 취소·만료 공통 경로, 취소 거절, 원장 실패 롤백, 지급액·쿠폰 배수 알림·재수락 중복 방지를 검증한다.

Postman은 JSON·스크립트 문법을 검사하고 모의 응답으로 전체 요청 흐름을 검증했다. 조기 지급, 배수 누락, 중복 지급, 중복 알림, 잘못된 알림, 쿠폰 미복구 응답을 실패로 검출하는 것도 확인했다. **실제 서버를 대상으로 한 Postman 실행은 아직 하지 않았다.**

## 승인·취소 오류의 기대 결과

- 최초 승인 요청이 명확한 INVALID_REQUEST 또는 내부 인증 실패로 거절되면 주문 실패와 예약 쿠폰 복구가 함께 반영된다. 같은 주문을 반복 요청해도 추가 복구하지 않는다.
- 앞선 타임아웃·처리 중 응답 이후 400·401을 받으면 승인·취소 결과를 조회한다. 조회 실패·기록 없음만으로 쿠폰을 복구하지 않는다.
- 최초 사용자 취소가 INVALID_REQUEST·내부 인증 실패로 거절되면 취소 기록만 종료한다. 결제·쿠폰은 유지하고 다른 진행 중 취소가 없으면 수락할 수 있다. 해당 취소를 다시 시도할 때는 새 취소 요청 키를 사용한다.
- 만료·로컬 실패 자동 취소의 인증 실패는 같은 키 재시도를 유지한다.

내부 API 키 오류는 전용 테스트 환경에서 검증해야 한다. 운영 키를 바꾸거나 정상 승인 시나리오 헤더로 401을 유도하지 않는다. 이 오류 경로는 Java 자동 테스트에서 검증하며, 현재 Postman 환경 파일의 비밀번호·토큰은 비어 있으므로 실제 실행 전 테스트 계정 정보를 준비해야 한다. 배포 시 V40 적용 순서는 [쿠폰 처리 문서](../order-coupons.md)를 따른다.

실제 만료 스케줄러 전체 실행·외부 결제 서버 장애 시나리오·룰렛 기회 및 경품의 취소 처리는 이 컬렉션의 검증 범위가 아니다.
