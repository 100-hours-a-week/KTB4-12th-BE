# 상품 조회수 통계 분리

구현 이슈: #407 → #408. 상품 데이터와 조회수 저장 위치를 분리하고 DB 이벤트를 배치 집계한다.

## 데이터 계약

- `product_view_stats.product_id`는 `products.id`를 참조하는 PK/FK이며 물리 삭제 시 함께 삭제한다.
- `views`는 NOT NULL이며 기본값은 0이다. `deleted_at`, `created_at`, `updated_at`을 함께 관리한다.
- V31은 기존 상품의 조회수·삭제 상태·생성/수정 시각을 이관한다.
- 상품 INSERT 트리거가 통계 행을 생성하고, 삭제 상태 변경 트리거가 통계 행의 삭제·복구 상태를 맞춘다.
- 런타임 JPA Product에서 조회수 필드를 제거한다. 카탈로그 INSERT 호환성을 위해 `products.views` 컬럼은 유지하지만 런타임 통계 원본으로 사용하지 않는다.

## 처리 흐름

요청 트랜잭션에서 상품 공유 잠금 → 기존 24시간 UPSERT 판정 → 인정된 이벤트 INSERT를 수행한다.
이력과 이벤트는 함께 커밋하거나 롤백하며, 저장 실패는 HTTP 성공 응답으로 숨기지 않는다.
요청 전체를 비동기로 실행하지 않는다. 조회수 통계는 응답 이후 배치로 반영하므로 인기순 반영에 지연이 있다.

V32의 `product_view_events`는 상품·사용자 FK, 처리 완료 시각, 삭제 상태, 생성/수정 시각과 미처리 인덱스를 가진다.
배치는 최대 500건을 `FOR UPDATE SKIP LOCKED`로 선점하고 상품 ID 순서로 합산한다.
통계 증가와 완료 표시는 READ_COMMITTED 단일 트랜잭션에서 처리한다. 통계 행 누락 또는 완료 건수 불일치 시 롤백한다.
삭제된 상품 이벤트는 완료 처리하되 통계는 증가시키지 않는다. 완료 후 복구하더라도 해당 이벤트를 소급 집계하지 않는다.
`app.scheduling.enabled` 설정을 따르며 기본 실행 간격은 1초다. 스케줄러 중단·실패 동안 남은 DB 이벤트는 재개 후 재처리한다.
외부 메시지 브로커나 메모리 큐를 추가하지 않는다. 배치 처리량을 초과하면 미처리 적체와 집계 지연이 증가한다.
일반 목록 및 AI 추천 목록의 통계 값, 인기순·선물순 정렬과 커서는 동일한 통계 테이블을 사용한다.

## 배포 및 검증

최신 develop 기준 V31 번호 충돌과 트리거 생성 권한을 확인한 후 배포한다.
테스트용 MySQL의 `log-bin-trust-function-creators` 설정은 트리거 생성 검증을 위한 설정이다.
DDL·트리거 마이그레이션 동안 쓰기 트래픽을 차단하고 이관 건수·값을 대조한 뒤 새 코드로 전환한다.
구버전 쓰기와 신버전 쓰기를 동시에 운영하면 `products.views`와 통계 테이블이 갈라지므로 롤링 전환 또는 구버전 코드만의 롤백은 지원하지 않는다.

실제 MySQL에서 이관, 상품 생성·삭제·복구, 24시간 정책, 동시 조회, 롤백, 일반·AI 추천 커서를 검증한다.
Elasticsearch의 조회수 동기화는 기존 #390 범위이며 이 변경으로 자동 동기화하지 않는다. ES 검색 활성화 환경의 최신 통계 반영은 별도 검증이 필요하다.

## 운영 확인

조회 이벤트는 이 변경에서 자동 삭제하지 않는다. 보관 기간과 처리 완료 이벤트 정리는 별도 운영 정책으로 결정한다.
이벤트 테이블 유실 또는 DB 자체 유실까지 복구하는 구조는 아니며 DB 백업·복구 정책을 따른다.
로컬 성능 비교는 [측정 보고서](https://app.notion.com/p/3fdce59041ef8179a288e6dadfe8c4bb)를 참고한다.
비동기 요청 큐 및 UPSERT 대체 알고리즘은 채택하지 않았으며 모든 부하 조건의 성능 향상을 보장하지 않는다.
