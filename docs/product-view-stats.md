# 상품 조회수 통계 분리

구현 이슈: #407. 상품 데이터와 조회수 저장 위치를 분리하며 이 단계에서는 동기 집계를 유지한다.

## 데이터 계약

- `product_view_stats.product_id`는 `products.id`를 참조하는 PK/FK이며 물리 삭제 시 함께 삭제한다.
- `views`는 NOT NULL이며 기본값은 0이다. `deleted_at`, `created_at`, `updated_at`을 함께 관리한다.
- V31은 기존 상품의 조회수·삭제 상태·생성/수정 시각을 이관한다.
- 상품 INSERT 트리거가 통계 행을 생성하고, 삭제 상태 변경 트리거가 통계 행의 삭제·복구 상태를 맞춘다.
- 런타임 JPA Product에서 조회수 필드를 제거한다. 카탈로그 INSERT 호환성을 위해 `products.views` 컬럼은 유지하지만 런타임 통계 원본으로 사용하지 않는다.

## 처리 흐름

요청 트랜잭션에서 상품 잠금 → 기존 24시간 UPSERT 판정 → 통계 증가를 수행한다.
이력과 통계 갱신은 함께 커밋하거나 롤백한다. 통계 행 누락은 정상 조회로 처리하지 않는다.
일반 목록 및 AI 추천 목록의 통계 값, 인기순·선물순 정렬과 커서는 동일한 통계 테이블을 사용한다.

## 배포 및 검증

최신 develop 기준 V31 번호 충돌과 트리거 생성 권한을 확인한 후 배포한다.
테스트용 MySQL의 `log-bin-trust-function-creators` 설정은 트리거 생성 검증을 위한 설정이다.
DDL·트리거 마이그레이션 동안 쓰기 트래픽을 차단하고 이관 건수·값을 대조한 뒤 새 코드로 전환한다.
구버전 쓰기와 신버전 쓰기를 동시에 운영하면 `products.views`와 통계 테이블이 갈라지므로 롤링 전환 또는 구버전 코드만의 롤백은 지원하지 않는다.

실제 MySQL에서 이관, 상품 생성·삭제·복구, 24시간 정책, 동시 조회, 롤백, 일반·AI 추천 커서를 검증한다.
Elasticsearch의 조회수 동기화는 기존 #390 범위이며 이 변경으로 자동 동기화하지 않는다. ES 검색 활성화 환경의 최신 통계 반영은 별도 검증이 필요하다.
